Instalação & Setup

O OAI Kit é um pacote npm que instala agentes de IA, comandos slash e protocolos de trabalho diretamente no repositório da equipe. Ele é agnóstico de IDE: suporta Claude Code e Cursor.

Pré-requisitos

RequisitoVersão mínimaObservação
Node.js18+Necessário para rodar o CLI do kit
Claude Code ou CursorQualquer versão recentePelo menos uma IDE com suporte a agentes/rules
Acesso ao Azure DevOps—Personal Access Token (PAT) para integração MCP
Git2.x+O kit cria branches e commits no padrão Praxio

Instalação por perfil

Rode o wizard interativo na raiz do repositório. Você escolhe quais IDEs e quais perfis instalar.

# Primeira instalação no repositório
npx praxio-oai-kit init

O wizard pergunta:

  1. IDE(s): Claude Code, Cursor, ou ambas
  2. Perfil(is): developer, qa, po (seleção múltipla)
  3. Organização Azure DevOps (URL base)

O que acontece automaticamente após o init:

  • O adaptador Claude gera os arquivos em .claude/agents/ e .claude/commands/
  • Se Cursor foi selecionado, o adaptador gera as regras em .cursor/rules/*.mdc
  • O .gitignore é atualizado: .mcp.json e .claude/.local-config.json são excluídos; .cursor/rules/ entra no gitignore apenas se Cursor não foi selecionado
  • Um template .mcp.json.template é criado para guiar a configuração do Azure DevOps

Adicionar um perfil depois

# Já tem developer, quer adicionar QA
npx praxio-oai-kit profile add qa

# Adicionar PO também
npx praxio-oai-kit profile add po

Adicionar uma IDE depois

# Já usa Claude Code, quer adicionar Cursor
npx praxio-oai-kit ide add cursor

Isso gera as rules em .cursor/rules/ e remove essa pasta do .gitignore, para que as rules sejam versionadas e compartilhadas com o time.

Atualizar o kit

npx praxio-oai-kit update

Aplica a versão mais recente do kit preservando sua configuração local (oai-kit.yaml).

Configurar MCP Azure DevOps

A integração com Azure DevOps usa o @azure-devops/mcp. Sem ela, os agentes ainda funcionam, mas exibem planos para criação manual em vez de criar automaticamente no Azure.

Claude Code

# Gera .mcp.json na raiz do projeto
npx praxio-oai-kit setup-mcp

Edite o .mcp.json gerado e preencha seu PAT (Personal Access Token) do Azure DevOps. O arquivo já está no .gitignore — cada dev mantém o seu localmente.

Cursor: O setup-mcp atual gera apenas o .mcp.json para Claude Code. Para usar com Cursor, copie as configurações do MCP para as Settings > MCP Servers do Cursor manualmente, usando o template em .mcp.json.template. Suporte nativo via .cursor/mcp.json está previsto em versões futuras do kit.

Primeiro uso no repositório

Após instalar o kit em um repositório novo, rode o bootstrap para gerar a memória institucional inicial (Speckit):

No Claude Code

/oai-kit-bootstrap-repo {NOME_DO_SISTEMA}

O agente:

  • Lê a estrutura do projeto, entrypoints e convenções de código
  • Gera os arquivos do .speckit/ (domain, architecture, known-issues, decisions, business-rules)
  • Posta um comentário inicial no Azure DevOps para rastrear o onboarding

Manutenção semanal: Use /oai-kit-update-speckit para manter o Speckit atualizado com mudanças recentes no código. O Speckit é a fonte primária de contexto — agentes o consultam antes de qualquer investigação.

Perfil Developer

Developer

O perfil DEV cobre o ciclo completo de desenvolvimento: da investigação de um bug até o deploy, passando por geração de patch, validação de testes, abertura de PR e quality gates. Também suporta features novas e revisão de PRs de colegas.

Comandos disponíveis

Use no Claude Code digitando o comando diretamente. No Cursor, os agentes são ativados contextualmente pelas rules — você pode invocar qualquer um pelo chat descrevendo o que precisa.

/oai-kit-analyze-bug {ID} DEV

Quando usar: Início de qualquer correção de bug — antes de tocar no código.

Investiga o root cause do bug com evidências de código (arquivo:linha obrigatório). Calcula o blast radius da correção: módulos afetados, integrações, banco de dados e risco classificado.

Automático
  • Lê o Speckit e a hierarquia da task no Azure
  • Localiza root cause com evidência de arquivo:linha
  • Gera BugReport + ImpactReport em .oai-flow/analysis/
  • Valida contra policies e ADRs
  • Pergunta confirmação de sigla do módulo
Manual (CP1)
  • Aprovar root cause e estratégia de correção
  • Confirmar sigla do módulo se solicitado
  • Só avança para generate-fix após aprovação
/oai-kit-generate-fix {ID} DEV

Quando usar: Após aprovação do CP1 (root cause confirmado).

Gera o patch mínimo seguindo RED→GREEN: exibe o plano antes de escrever código, escreve o teste que falha, implementa o mínimo, exibe Gate Pré-Commit com todos os arquivos alterados antes de commitar.

Automático
  • Propõe branch no padrão Praxio
  • Exibe plano de implementação antes de escrever código
  • Escreve teste RED antes do código
  • Implementa patch mínimo (GREEN)
  • Valida arquitetura condicionalmente (se risco alto)
  • Exibe Gate Pré-Commit (arquivos + mensagem) antes de commitar
  • Salva Patch em .oai-flow/delivery/
Manual (2 gates + CP2)
  • Aprovar plano antes de implementar
  • Aprovar Gate Pré-Commit antes de commitar
  • CP2: aprovar patch gerado para prosseguir para testes
/oai-kit-run-regression {ID} DEV

Quando usar: Após aprovação do CP2 (patch aprovado), antes de abrir o PR.

Valida a suíte de testes: confirma que o teste RED agora passa (GREEN), verifica cobertura complementar e executa o gate check de qualidade.

Automático
  • Verifica RED→GREEN do teste gerado
  • Analisa cobertura dos módulos afetados
  • Escreve testes complementares se necessário
  • Gera ValidationReport em .oai-flow/delivery/
Manual
  • Executar os testes localmente
  • Confirmar se os resultados batem com o esperado
/oai-kit-open-pr {ID} DEV

Quando usar: Após validação de testes — hora de submeter o trabalho.

Cria o PR no Azure DevOps com título e descrição no padrão Praxio (igual à primeira linha do commit), linka às tasks e preenche automaticamente o fechamento de desenvolvimento.

Automático
  • Título = primeira linha do commit
  • Descrição = commit completo + arquivos + como testar
  • Linka PR às tasks do Azure
  • Preenche Task de Fechamento Dev
  • Salva PR em .oai-flow/delivery/
Manual (CP3)
  • Revisar o PR criado no Azure DevOps
  • Aguardar aprovação do code review
/oai-kit-release-check {ID} DEV

Quando usar: Após aprovação do PR — antes do deploy.

Verifica quality gates, janela de release (horário permitido, freeze ativo?) e gera o release package. Após deploy confirmado, aciona o learning agent para atualizar o Speckit e fechar a task.

Automático
  • Verifica todos os quality gates da release policy
  • Valida janela de release e freeze ativo
  • Gera ReleasePackage + plano de rollback
  • Pós-deploy: atualiza Speckit (Known Issues, ADRs)
  • Fecha tasks de dev e QA no Azure
  • Salva métricas em .speckit/incidents/metrics-feed.jsonl
Manual
  • Executar o deploy
  • Confirmar sucesso do deploy ao agente
/oai-kit-feature {ID} DEV

Quando usar: Feature nova — sem bug prévio investigado.

Fluxo completo de feature: lê a US no Azure, extrai critérios de aceite, propõe escopo (CP1), detalha plano de tasks (CP2), implementa, abre PR e conduz até o release. Pede confirmação da sigla do módulo antes de criar branch.

Automático
  • Busca US + critérios de aceite no Azure via MCP
  • Propõe escopo, exibe plano e aguarda aprovação
  • Gera plano de tasks com estimativas (Large)
  • Por task: exibe o que vai implementar e aguarda ok
  • Implementa seguindo RED→GREEN
  • Gate Pré-Commit: exibe arquivos alterados + mensagem e aguarda ok
  • Branch, commits e PR no padrão Praxio
  • Gate Pós-Implementação: exibe resumo antes de abrir PR
Manual (5 gates)
  • CP1: aprovar escopo da feature
  • CP2: aprovar plano de tasks (Large)
  • Gate por task: aprovar plano antes de implementar
  • Gate Pré-Commit: aprovar arquivos e mensagem antes de commitar
  • Gate Pós-Implementação: aprovar antes do PR
  • CP3: aprovar o PR no Azure
/oai-kit-refine-card {ID} DEV

Quando usar: Cerimônia de refinamento — analisa a task antes da sprint.

Lê a task no Azure, consulta o Speckit, identifica impactos técnicos, riscos e dependências. Posta um comentário estruturado diretamente na task no Azure para servir de contexto durante a cerimônia.

Automático
  • Navega hierarquia da task (Epic → Feature → US)
  • Extrai SIM/PSE da Feature
  • Consulta Speckit para contexto técnico
  • Posta análise como comentário no Azure via MCP
Manual
  • Revisar e complementar o comentário postado
  • Conduzir a discussão de refinamento com o time
/oai-kit-review-pr {N} DEV

Quando usar: Para revisar o PR de um colega antes de aprovar.

Revisa o PR sob 4 dimensões: funcionalidade (critérios de aceite atendidos?), qualidade de código (policies, anti-patterns), padrões Praxio (branch, commit, PR title) e testes. Emite parecer com pontos de atenção.

Automático
  • Lê o PR e a US vinculada no Azure
  • Verifica conformidade com coding-principles.md
  • Identifica violações de security-policy.md
  • Checa padrões de branch/commit/PR title
Manual
  • Decisão final de aprovar ou reprovar o PR
  • Comunicar feedback ao autor

Automático vs Manual — DEV

Gates de confirmação obrigatórios: todo agente que realiza ações (escrever código, commitar, criar PR, atualizar Speckit) para, exibe o que vai fazer e aguarda uma resposta explícita do dev ("sim", "pode", "ok") antes de prosseguir. Silêncio ou contexto implícito nunca são interpretados como aprovação.

Boas práticas — DEV

  • 1
    Nunca pule o analyze-bug. Mesmo que o bug pareça óbvio, a análise garante que o blast radius foi considerado e que a sigla do módulo está correta. Fixes sem análise tendem a gerar efeitos colaterais.
  • 2
    Speckit First. Os agentes consultam .speckit/ antes de qualquer busca no código. Mantenha-o atualizado com /oai-kit-update-speckit semanalmente — isso melhora a qualidade das análises de toda a equipe.
  • 3
    Minimum Viable Patch. O builder-agent só implementa o mínimo. Não peça refactoring durante um fix de bug — abra uma task separada. Patches pequenos têm blast radius menor e são mais fáceis de revisar.
  • 4
    Policies são hard stops. Os arquivos em .oai-kit/policies/ são bloqueadores absolutos. Se um agente recusar uma ação com base em policy, não tente contornar — a policy existe por um motivo arquitetural ou de segurança.
  • 5
    Multi-repo: confirme antes. Se a task envolver mais de um repositório (ex: mudança de contrato de API), o agente perguntará o caminho local do outro repo. Forneça — ou diga que não é necessário. O agente nunca modifica outro repo sem confirmação explícita.
  • 6
    Confirme o deploy antes de fechar. O /oai-kit-release-check aguarda sua confirmação de que o deploy foi bem-sucedido antes de acionar o learning agent. Não confirme automaticamente — verifique os logs.
Perfil QA

Quality Assurance

O perfil QA cobre planejamento de testes, refinamento, regressão, validação de critérios de aceite e documentação de defeitos — tudo integrado ao Azure DevOps via MCP. A base de conhecimento QA se alimenta automaticamente a cada plano criado.

Comandos disponíveis

/oai-kit-qa-plan {ID} QA

Quando usar: Para criar ou atualizar um plano de testes — em Refinamento (sem PR) ou em Execução (PR já existe).

Pergunta o modo (Refinamento ou Execução) e se é criação ou atualização. Busca a US e critérios de aceite no Azure, cruza com o código (se PR existir) e gera cenários de teste numerados (CTxx.xx) com passos, resultado esperado e evidência. Cria os Test Cases no Azure via MCP.

Automático
  • Busca US + critérios de aceite no Azure
  • Valida consistência: cada critério tem CT?
  • Gera cenários: principal, alternativo, erro
  • Cria Test Cases no Azure (steps em XML)
  • Oferece salvar índice da suíte em .oai-kit/knowledge/qa/test-suites/
Manual
  • Confirmar área, sprint e nome da suíte
  • Revisar cenários gerados antes de salvar
  • Decidir se salva o índice localmente
/oai-kit-qa-refine-card {ID} QA

Quando usar: Cerimônia de refinamento — perspectiva QA sobre a task.

Analisa a task sob a ótica de qualidade: identifica lacunas nos critérios de aceite, cenários de borda não cobertos, dependências de dados de teste e riscos de regressão. Posta análise como comentário na task do Azure.

Automático
  • Navega hierarquia da task no Azure
  • Identifica lacunas nos critérios de aceite
  • Sugere cenários de borda e risco de regressão
  • Posta análise como comentário no Azure via MCP
Manual
  • Complementar o comentário com contexto adicional
  • Conduzir discussão de QA no refinamento
/oai-kit-qa-regression {ID_PR} QA

Quando usar: PR aberto — para saber o que precisa ser testado por regressão.

Analisa os arquivos alterados no PR e mapeia quais suítes e cenários de regressão devem ser executados, consultando o índice em .oai-kit/knowledge/qa/test-suites/. Quanto mais suítes indexadas, mais preciso o mapeamento.

Automático
  • Lê arquivos alterados no PR via MCP
  • Consulta índice de suítes na knowledge base
  • Mapeia: arquivo alterado → módulo → suítes relacionadas
  • Prioriza CTs por risco (Alta → Média → Baixa)
Manual
  • Executar os cenários mapeados
  • Registrar resultados no Azure
/oai-kit-qa-validate {ID} QA

Quando usar: Para verificar se o código implementado no PR cobre todos os critérios de aceite da US.

Cruza critérios de aceite da US com o diff do PR. Identifica critérios sem cobertura, comportamentos implementados não descritos na US, e emite um parecer de conformidade.

Automático
  • Busca US + critérios no Azure
  • Lê diff do PR
  • Cruza cada critério com o código
  • Emite: ✅ Coberto / ⚠️ Parcial / ❌ Não coberto
Manual
  • Decidir se reprova o PR com base no parecer
  • Comunicar ao dev critérios não cobertos
/oai-kit-qa-bug {ID} QA

Quando usar: Quando encontrar um defeito durante execução de testes.

Estrutura o defeito encontrado: qual CT falhou, comportamento esperado vs real, evidência. Cria uma Task de Ajuste no Azure vinculada à US com título [AJUSTE] CTxx.xx — descrição.

Automático
  • Estrutura o defeito com campos padronizados
  • Cria Task tipo "Ajuste" no Azure via MCP
  • Vincula à US de origem
  • Define prioridade com base no risco
Manual
  • Fornecer descrição do defeito e evidência
  • Informar o CT onde foi encontrado
  • Confirmar prioridade

oai-kit-qa-refiner

oai-kit-bug-analyzer

Base de conhecimento QA

A knowledge base fica em .oai-kit/knowledge/qa/ e alimenta os agentes de planejamento e regressão. Quanto mais rica, mais preciso o mapeamento automático de regressão.

PastaO que armazenarQuem preenche
test-suites/ Índice de suítes criadas: IDs Azure, escopo (US/módulo/sprint), CTs e arquivos relacionados Automático — agente oferece salvar após criar no Azure
processes/ Processos de teste do time: como testar módulos específicos, pré-condições globais, dados de ambiente Manual — QA cria e edita os .md conforme necessário
documentation/ Documentação de referência: fluxos de negócio, regras de aceite globais, glossário de teste Manual — QA importa documentação existente

Loop automático: após confirmar a criação de um plano no Azure, o agente pergunta se quer salvar o índice da suíte em test-suites/{modulo}-{nome-suite}.md. Esse arquivo é lido pelo regression-planner em futuros PRs para mapear automaticamente o que precisa ser retestado.

MCP Azure DevOps — QA

A integração MCP permite criar Test Cases, Test Plans e Tasks diretamente no Azure sem sair do chat.

Claude Code

npx praxio-oai-kit setup-mcp
# Edite .mcp.json com seu PAT do Azure DevOps

Cursor

Suporte nativo via .cursor/mcp.json está previsto em versões futuras. Enquanto isso:

  1. Abra as Settings do Cursor
  2. Vá em MCP Servers
  3. Adicione manualmente a configuração do .mcp.json.template (na raiz do projeto)
  4. Preencha seu PAT do Azure DevOps no campo env.AZURE_DEVOPS_PAT

Sem MCP: os agentes ainda funcionam. Exibem o plano completo com instruções para criação manual no Azure e geram os arquivos de índice localmente com IDs marcados como [pendente] para atualização posterior.

Boas práticas — QA

  • 1
    Salve o índice da suíte sempre que criar um plano. O agente pergunta após criar no Azure — confirme. Isso torna o mapeamento de regressão progressivamente mais preciso a cada sprint.
  • 2
    Use Refinamento para antecipar cenários de borda. Executar /oai-kit-qa-refine-card e /oai-kit-qa-plan no modo Refinamento antes da sprint reduz surpresas na execução e deixa os desenvolvedores cientes dos casos de teste desde o início.
  • 3
    Revise cenários antes de salvar. O agente gera uma boa cobertura, mas você conhece nuances de ambiente e dados de teste que ele não conhece. Adicione pré-condições específicas antes de confirmar a criação no Azure.
  • 4
    Popule processes/ com contexto de ambiente. Documente: como preparar dados de teste, credenciais de homologação, ordem de execução de suítes. Os agentes leem essa pasta antes de planejar — informações lá evitam perguntas repetitivas.
  • 5
    Use /qa-validate antes de aprovar PRs críticos. Especialmente em features com muitos critérios de aceite — o agente cruza cada um com o código do PR e destaca o que ficou de fora.
Perfil PO

Product Owner

O perfil PO cobre documentação de demandas, prototipação, refinamento e verificação visual de entregas. Os agentes trabalham integrados ao Azure DevOps para criar e preencher work items no padrão Praxio.

Comandos disponíveis

/oai-kit-po-document {ID} PO

Quando usar: Para documentar uma demanda nova ou complementar uma US existente com descrição, critérios de aceite e DoR.

Lê o contexto da demanda (SIM/PSE, Feature e inputs do PO), gera descrição estruturada, critérios de aceite em linguagem testável e checklist de DoR (Definition of Ready). Atualiza a work item no Azure via MCP.

Automático
  • Lê Feature e contexto de negócio no Azure
  • Consulta templates em knowledge/po/demand-templates/
  • Gera descrição + critérios de aceite
  • Checklist DoR preenchido
  • Posta/atualiza a work item no Azure via MCP
Manual
  • Fornecer contexto de negócio e restrições
  • Revisar e aprovar antes de preencher no Azure
/oai-kit-po-prototype {ID} PO

Quando usar: Para especificar o comportamento visual e de interação de uma tela ou fluxo.

Com base na US e nos padrões visuais em knowledge/po/visual-patterns/, gera especificação de protótipo: fluxo de telas, estados, mensagens de erro e regras de validação visual. Serve de referência para DEV e QA.

Automático
  • Lê padrões visuais da knowledge base
  • Gera especificação de estados da tela
  • Descreve fluxo de interação e validações
  • Salva spec em .oai-flow/discovery/{ID}-prototype.md
Manual
  • Descrever o objetivo da tela e restrições de negócio
  • Revisar especificação antes de compartilhar com o time
/oai-kit-po-refine-card {ID} PO

Quando usar: Cerimônia de refinamento — análise da task sob perspectiva de produto.

Analisa a task no Azure, verifica se a US está pronta para desenvolvimento (DoR), identifica dependências de produto e ambiguidades nos critérios de aceite. Posta análise como comentário na task do Azure.

Automático
  • Verifica completude do DoR da US
  • Identifica critérios ambíguos ou ausentes
  • Mapeia dependências de outras US ou sistemas
  • Posta análise como comentário no Azure via MCP
Manual
  • Complementar análise com contexto de negócio
  • Resolver dependências identificadas
/oai-kit-po-scan-visual {ID} PO

Quando usar: Após entrega de uma tela — para verificar se implementação segue os padrões visuais definidos.

Compara a implementação entregue (via PR ou screenshots) com os padrões visuais em knowledge/po/visual-patterns/ e a especificação de protótipo. Emite relatório de conformidade visual.

Automático
  • Lê padrões visuais da knowledge base
  • Compara com a especificação do protótipo
  • Lista desvios encontrados por categoria
  • Emite: ✅ Conforme / ⚠️ Desvio / ❌ Não conforme
Manual
  • Fornecer screenshots ou descrever a tela entregue
  • Decidir se aceita desvios ou solicita ajuste

Boas práticas — PO

  • 1
    Popule visual-patterns/ antes de usar /po-prototype. O agente usa os padrões registrados como referência. Sem eles, a spec gerada será genérica. Importe o guia de estilo ou design system do produto — mesmo um resumo já melhora muito o resultado.
  • 2
    Use /po-refine-card antes do refinamento. O comentário postado no Azure serve de pauta técnica para a cerimônia. Compartilhe o link do card com o time antes da reunião — economiza tempo de contextualização.
  • 3
    Critérios de aceite em linguagem testável. O agente escreve critérios no formato "dado X, quando Y, então Z". Prefira esse padrão — facilita a vida do QA e evita interpretações ambíguas durante o desenvolvimento.
  • 4
    Revise tudo antes de preencher o Azure. Os agentes sempre pedem confirmação antes de atualizar work items. Nunca deixe passar sem ler — uma descrição incorreta postada na task é vista pelo time todo e gera retrabalho.
  • 5
    Mantenha project-context/ por sprint. Objetivos e prioridades mudam. O agente de documentação lê esse contexto para calibrar tom e prioridade nos critérios gerados. Um contexto desatualizado gera critérios fora de foco.
